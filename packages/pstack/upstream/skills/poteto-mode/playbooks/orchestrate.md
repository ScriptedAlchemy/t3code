### Orchestrate

**You run the program, never the code. Decide which agent does each piece of work, then check what each one produces.** For a standing project handed to one coordinator chat: multi-day, many stacked PRs, dozens to hundreds of subagents, few human turns. One task driven to a predicate is Autonomous run. One ambitious run that needs a bespoke workflow is figure-it-out. Work that one agent could finish inside the session's budget is not a program.

Run it through T3 orchestration. Call `orchestrator_capabilities` before delegation and respect its nesting and concurrency limits. Spawn workers with `delegate_task`, copying the role's resolved target and complete options from `<t3_pstack>`; an inherited seat omits `target`. Keep project notes beside `<models>` under `orch/<repo-name>/`, outside the replaceable pack. The parent links and watches PRs through `link_pull_request` and `watch_pull_request`; workers return the PR URL, head SHA, and pending checks. Child completion and PR events wake the parent. End the turn while waiting. Run no polling loops and keep no second scheduler or agent ledger.

#### Topology

- **One owner per PR.** The owner is the only writer of its branch and carries the PR from build to merge. Only the owner pushes, rebases, or retargets it. Closing or retargeting a base PR orphans every PR above it, so the owner does that only on your call. You never author or edit code. Conflicted merges, chain rebases, and fixes go to owners.
- **A fresh worker for each independent task.** Its kickoff carries everything it needs, including each upstream report it depends on, pasted in full. Workers can't see their siblings. Use `isolation: "worktree"` for independent code edits. A worktree starts at the parent checkout's committed local HEAD and stays on this environment. Arrange the committed base within the task's authorization first; a branch name in the brief does not change it. Use the shared checkout only for a browser or device check, a simulator, or auth available only there, with a single writer. Include the absolute pack/models paths and relevant resolved roles in every brief; never change effort or speed from the resolved target.
- **A sub-coordinator only when one area has many parallel workers.** It owns that area's workers and kickoffs and sends you one rollup, never raw worker reports. Stop at three levels: you, sub-coordinators, and workers. Keep a bounded rolling window within the advertised T3 concurrency limit, and start the next worker as each finishes instead of waiting on a whole batch.
- **Use a fresh delegate for every task and review round.** T3 does not fork a worker's process state. Preserve committed work and artifacts, then give the new worker a consolidated brief with the prior findings, branch, head SHA, and remaining work. Arrange its checkout base explicitly. Retain every `taskId`, cancel replaced work with `task_cancel`, and use a new `clientRequestId` for new work; retries of the same launch keep the same key and arguments. Never poll or message a child to check on it.
- **Each PR gets a verifier that isn't its author,** on a different model family. The owner merges only with the task's merge authorization and that verifier's pass at the current head. Each owner returns pending checks to the parent; the parent delegates any later fix or merge as a fresh task.
- **Start with one unit.** Take it through kickoff, owner, verifier, and merge before you fan out, so a flaw in the kickoff costs one agent instead of fifty. On near-identical cheap units, the first unit is that test.

#### Supervision

- **Each kickoff names the evidence that proves the work is done,** such as a command and its expected output, a browser or device check, or an artifact. It also names the goal, the paths the worker may and may not write, and the actions it must not take. If you can't name the evidence, the unit isn't scoped yet.
- **Read the diff or the artifact, not only the worker's summary.** Green CI is an input to a verdict, not a verdict. Behavioral work needs more than a type check. A verdict covers one head SHA, so a new push needs a new verdict. Read a sample of each sub-coordinator's kickoffs while its workers run, and fix its instructions when one fails.
- **Send back work that drifts from scope or grows past what was asked.** Keep only the fixes that block the program, and park the rest as follow-ups.
- **Check a PR's live state before you report on it,** with `gh pr view` and `gh pr checks` or your forge's equivalents, not the worker's last report. Account for every worker you spawned as done, replaced, or absorbed into another worker's scope.
- **Stop or replace a worker that stalls or loops.** Judge it by its pushes and PR activity, not its status text. Retry by cause: a smaller scope after a context or memory limit, the same kickoff after a dropped connection, and a different model after a tool error. After two retries, drop the unit and replan around it. When a stopped worker returns late, check its result against the PR's current state, and hand any unique findings to a fresh worker.
- **Ask the user only for a real decision or a blocker,** such as an irreversible action, a product or preference call that no experiment settles, or a dead end that survived a replan. Rebase mechanics, retries, CI flakes, review triage, and "should I keep going" never reach the user.

**Reply:** what landed against the goal, each PR's live state and verdict with its link, what was dropped and why, and the decisions waiting on the user.

Retain every `scheduledTaskId` for an explicitly needed heartbeat and delete it with `delete_scheduled_task` at completion or cancellation. Include the absolute pack/models paths and resolved roles in scheduled prompts. Never schedule a child-status poll.
